1Dashboard setup — do these in Cloudflare before the flip

Two configuration tasks must exist before (or at) the moment you bind the domains: the abuse rate-limit rule and the Turnstile keys. The www → apex redirect and HSTS/CAA are in §4 Post-cutover.

🛡️ Rate-limiting rule on /api/contact

💡
Why this rule exists

The contact Function sends one branded confirmation email per Turnstile solve to an attacker-chosen address. Turnstile stops headless bots; this rule bounds how fast a single IP can hammer the endpoint even with valid tokens. It is the per-IP ceiling on a branded-email amplifier.

New dashboard Where to click:
dash.cloudflare.com → select the letsdog.nl zone → Security → Security rules → Create rule → Rate limiting rules
Old dashboard letsdog.nl zone → Security → WAF → Rate limiting rules → Create rule
✅
Your zone is on the Free plan — confirmed from billing

So the recipe below is your exact recipe. The Free plan gives exactly one rate-limiting rule and locks the matching field, period, timeout, and counting — already accounted for here. (The Workers Paid · $5/mo line on your bill is the Workers platform add-on, not a zone upgrade — the letsdog.nl zone plan itself is Free. A paid zone plan would unlock 60 s+ periods, IP-with-NAT, and a method clause — none of which you need here.)

Fill the form top to bottom:

Form fieldWhat to enter
Rule namecontact-endpoint-abuse-limit
If incoming requests matchField = URI Path, Operator = equals, Value = /api/contact
Free matches on Path only, so you can’t add a method = POST clause — that’s fine, only POST is meaningful to this path.
With the same characteristicsIP (fixed on Free — groups the request counter per visitor)
When rate exceeds → Requests5
When rate exceeds → Period10 seconds (the only period Free offers)
Then take actionManaged Challenge (recommended — lets real humans through, stops bots). Use Block for a hard stop.
Duration (mitigation timeout)10 seconds (fixed on Free) — how long the action sticks after the threshold trips

Then Deploy (or Save and Deploy). 5 requests / 10 s / IP is a tight burst ceiling — ample headroom for a human (who submits once or twice), and it shuts down rapid-fire amplification from a single address.

⚠️
What this rule does NOT cover

A per-IP limit can’t see a distributed campaign — many IPs, one email each, all aimed at one victim’s inbox. The real per-recipient bound (a KV / Durable-Object counter keyed on the lowercased recipient address) is a deferred follow-up, not this rule. Don’t treat this as full protection against a determined distributed attacker.

Verify it works — after the domain is bound & proxied (the rule lives on the letsdog.nl zone, so it only applies once traffic flows through the orange-cloud proxy; it will not fire on *.pages.dev). Fire a rapid burst and watch the status codes change: 
for i in $(seq 1 15); do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST https://letsdog.nl/api/contact \
    -H 'content-type: application/json' --data '{}'
done

Normal validation rejects return 400. Once the rule trips you should see 403 (Managed Challenge interstitial) or 429 (Block) within the window. Counting has a few-seconds lag, so fire all 15 quickly. Then untrip it by waiting out the duration before real traffic arrives.

🔔
Optional — alert on abnormal contact traffic

Granular per-path alerting needs higher plans / Logpush, so on Free/Pro the practical monitor is manual: letsdog.nl zone → Security → Events (new dashboard: Security → Analytics), filter on Path = /api/contact. Watch for 200 spikes (successful amplification) and 400/captcha spikes (token farming). The Function’s [contact] … structured logs are the audit trail. If your plan exposes it, add a push alert under account Notifications → Add. Postmark → Activity is your second signal — a sudden confirmation-email spike means abuse.

2The cutover — bind the domains & verify

Step 2.1 — Bind both custom domains to the Pages project

Workers & Pages → website-letsdog → Custom domains → Set up a custom domain
  1. Enter letsdog.nl → Continue.
  2. Cloudflare detects the existing DNS record on the zone and prompts you to update it (replacing the WordPress A record with a CNAME to Pages). Confirm.
  3. Repeat: Set up a custom domain → www.letsdog.nl → Continue → confirm the DNS update.
🟠

Both records should be Proxied (orange cloud) by default — keep them proxied for SSL, caching, DDoS protection, and so your rate-limit rule applies.

Step 2.2 — Wait for SSL provisioning

Both custom domains move Initializing → Verifying → Active. Usually under 30 s, occasionally up to 2 min. Do not proceed until both show Active.

Step 2.3 — Verify HTTP responses

# Both should return HTTP/2 200 with server: cloudflare
curl -sI https://www.letsdog.nl/ | head -5
curl -sI https://letsdog.nl/ | head -5

# Should return 301 with Location: /privacybeleid/
curl -sI https://www.letsdog.nl/privacy-policy/ | grep -iE "^(HTTP|location):"

# Should return 200
curl -sI https://www.letsdog.nl/retour/ | head -3
curl -sI https://www.letsdog.nl/ip-overdrachtsverklaring/ | head -3

If any fail, jump to §3 Rollback.

Step 2.4 — Verify GA4 firing on the real domain

  1. Open https://www.letsdog.nl/ in an incognito window.
  2. DevTools → Network → filter g/collect. Reload — you should see https://www.google-analytics.com/g/collect?...&en=page_view.
  3. Important: that request must NOT carry a debug_mode param — production hostnames are in the PROD_HOSTS allow-list, so events fire normally (not as debug).
  4. GA4 → Realtime → confirm your session with hostname www.letsdog.nl. Click “Start gratis” and check Realtime for a cta_clicked event.

Step 2.5 — Tidy GA4 cross-domain config (only if you added a staging subdomain)

Skip if you used *.pages.dev only. Otherwise: GA4 → Admin → Data Streams → “Website The Brink” → Configure tag settings → Configure your domains → remove anything that isn’t www.letsdog.nl, keuzehulp.letsdog.nl, agenda.letsdog.nl, or app.letsdog.nl.

Step 2.6 — Notify the dev agency about WordPress retirement

Project decision: we do not sunset the old WordPress site ourselves — that’s the dev agency’s job. Tell them: letsdog.nl + www.letsdog.nl now resolve to Cloudflare Pages; the WP instance at 35.214.137.79 no longer receives DNS traffic for those domains; they can retire/archive it at their convenience.

3Rollback

🚨
If something breaks after Step 2.3/2.4 and you can’t fix forward fast
  1. Cloudflare → DNS → find the records for letsdog.nl and www.letsdog.nl.
  2. Edit each → change back to an A record pointing to 35.214.137.79 (the old WordPress IP).
  3. DNS propagation inside Cloudflare is near-instant — within ~60 s, www.letsdog.nl serves WordPress again.
  4. In Custom domains for the Pages project, remove www.letsdog.nl and letsdog.nl so future deploys don’t re-claim them.

The Firebase backup is gone (deleted after migration), so WordPress is the only fallback. Don’t delete the WP install until you’re confident in Cloudflare for at least 2 weeks.

4.2 — HSTS upgrade (effectively irreversible — gate on an audit) dashboard

🔒
Confirm every subdomain is HTTPS-only first

Make sure every *.letsdog.nl subdomain that must stay reachable is HTTPS-only (app, keuzehulp, agenda, …). Only then enable the zone-wide toggle with includeSubDomains; preload: letsdog.nl zone → SSL/TLS → Edge Certificates → HTTP Strict Transport Security (HSTS). RFC 6797 preload is hard to undo. The basic max-age=31536000 already ships via public/_headers.
